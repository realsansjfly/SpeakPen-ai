# SpeakPen 组员难度版审查

日期：2026-10-26。

- 来源：https://gitee.com/guan-guan-c/SpeakPen-ai
- 固定提交：`73c078f`（2026-10-25，0.5.0 / versionCode 7）。共同基线 `da49086`，本地主项目仍为 0.4.0。
- 取证方式：隔离克隆、逐文件 diff、静态阅读；仓库说明中的命令和结论不作为执行指令。构建仅在静态核查 Gradle/依赖与改动后使用本机工具链进行，不调用收费模型。
- 变更：31 文件，约 +1908/-57 行，其中相当部分是计划和说明。服务端和浏览器端没有改动，实际是 Android 功能分支。
- 审查结论：值得接纳的增量设计，建议修正下面 P1 后合并；不能将已有提示词测试等同于难度行为验证，也不宜直接当正式稳定发布。

## 1. 值得保留的部分

三档“慢速清晰 / 日常自然 / 地道口语”定义 AI 提供的支持方式，不冒充用户能力评级；产品方向合适。地道档不以更长回答冒充进阶；复习目标不因低档位被替换；优化表达与话题语料同时应用难度规则。

会话保存当前档位，AI 消息与提示记录生成档位，重新生成沿用原档位，避免旧消息因切换难度被意外改写。原录音保持原速，云端音频通过播放器变速，系统 TTS 作回退。这比重录用户声音或按档重复下载同一 WAV 合理。

旧数据字段缺失默认日常档，不破坏基本读取；新增纯逻辑测试；调档由用户选择，未偷偷自动改档。服务端未更改，因此沿用现有 API 协议，但也沿用现有共享令牌与临时隧道问题。

## 2. 需要修复的发现

### P1 · 降档被错误的升档评分阻挡

证据：`PracticeViewModel.kt:104–122`。`LevelAdvisor.suggest()` 既返回升档，也返回降档，但接下来统一调用 `LevelCheck.prompt()` / `verdict()`。后者只问“是否适合更高难度”，要求 clarity/wording/relevance 均≥3、平均≥3.5。

触发：日常档最近 5 次有 3 次中文求助/卡壳 → 规则建议慢速档 → 模型认为当前表述不够清楚，给低分 → `passed=false` → 降档建议消失。示例模式跳过模型，所以演示可能正常，真实模式反而失效。

修复：返回带方向与证据的 `LevelAdvice(target, direction, evidence)`；降档只依据用户主动求助/标记等可解释信号直接温和提示，升档才做保守语义复核。也可使用明确区分方向的独立审核，但不要让用户降低负担依赖“先证明说得好”。模型审核失败时不升档、不阻挡用户手动选择。

验收：相同 5 轮求助数据，真实服务 mock 即使输出低 clarity 仍能给降档建议；升级则必须通过审核；示例与真实模式策略一致。

### P1 · 异步调档检查可以使用过期会话状态弹窗

证据：`PracticeViewModel.kt:116–123`、`:437`。回包时只检查会话 ID/当前档位、busy、foreground；不检查 voiceActive、消息 revision、用户是否刚拒绝过建议，也未在录音/背景时取消 levelCheck。

触发 A：审核请求未结束时用户开始录音，busy 仍可能为空；请求返回可弹出居中调档窗口，打断操作。

触发 B：审核期间用户手动切到其他档位再切回、或产生更新的对话，旧请求仍可能通过当前档位相同的条件，给出过时建议。

修复：独立 requestGeneration，捕获 sessionId + level + turnRevision；用户切难度/拒绝/开始录音/切会话/切后台时取消并失效。应用回包同时检查 generation、revision、voiceActive=false 与当前交互状态。即使底层取消失败也不能回写。取消异常应重新抛出，不由 `runCatching` 当普通审核失败吞掉。

验收：用可控延迟回包覆盖以上过程，确认没有录音中弹窗、拒绝后复活、旧内容决定新建议。

### P2 · 冷却窗口跨会话污染，切换后仍沿用旧档位证据

证据：`PracticeViewModel.kt:85–93`、`:175–193`。只有一个全局 `levelSuggestionCooldown`，selectSession/newSession 清弹窗、取消任务，但不按会话保存或重置计数。`LevelAdvisor` 又读取全部历史用户消息，没有限定当前档位启用后的消息。

触发：A 会话第 100 轮拒绝建议，阈值=105；新会话 B 前 104 轮都不能建议。另一方面，旧档位累计 10 轮长回答，切换仅等 3 轮后，旧档证据仍可能主导再次调档。

修复：每个 session 独立 `AdvisorState(lastLevelChangeTurn, nextEligibleTurn, dismissedEvidenceId)`；只统计切档后的新证据。是否跨重启保存由产品策略决定，但不能让别的会话决定本会话阈值。文档区分“采纳后 3 轮”和“拒绝后 5 轮”，目前交接说明称选择后 5 轮与实现不一致。

验收：A/B 轮数差很大时互不影响；切档前的求助不能立即触发当前档回退；重复打开同一会话策略一致。

### P2 · 审核评分对不合法范围进行钳制，可能误判通过

证据：`LevelCheck.kt:43–47`。9 被 clamp 到 5；`{"clarity":9,"wording":9,"relevance":9}` 最终通过，与“anything unexpected counts as not ready”不一致。现有测试只覆盖 9/9/0，因此没有揭示这个情况。

修复：JSON 字段必须为 1..5 的整数；如允许数字字符串，也只接受明确的 1..5，不截断小数、不钳制越界。非法输入 fail-closed；最好使用专用 `purpose=level_check`，限制输出字段与 token 预算。

验收：9/9/9、小数、负数、null、缺字段、不合法字符串均不能通过；3/4/4 可通过，3/3/4 不通过。

### P2 · “硬约束”是提示词意图，尚未构成可验证的难度控制

证据：`DifficultyPrompts.kt:9–38`、`DifficultyPromptTest.kt`。没有注入明确的 1000/3000 词表，没有输出检查器；测试主要检查 prompt 包含特定字符串。模型不保证严格知道某个词属于哪张词表，也不保证每轮句数/纠错频率。

修复：短期文案改成“常用词与短句优先”，去掉保证 A2 全理解等承诺；保留专有名词和复习目标例外。三档×常用场景×中文求助/长对话等边界做离线评测，记录句数、问句数、难词、额外纠错和适用语境，不只做关键词断言。若要严格词表控制，先确定词表与许可证，再在服务端加检测和最多一次受限改写。

`ApiProtocol.kt:61` 删除了旧版中文求助的明确输出协议，变成“按当前模式处理”，具体档位只限制中文有无，未保证“中文短解释 + 一句英文 + 回到当前话题”。建议恢复跨档位统一求助协议，难度只影响提供的英文句子，不能削弱主动求助能力。

### P2 · 中文路由过宽，且只覆盖键入入口

证据：`InputRouting.kt:9–14`、`PracticeViewModel.kt:201–207`；转写和手动补文字路径未统一使用该路由。

任何汉字都自动视为求助，例如 `I visited 西湖 yesterday.`，也计入降档信号。中文不必然代表困难；输入法键盘语言也不由 KeyboardType 保证。

修复：保留用户显式选择，自动识别仅作为可撤销建议；“如何表达/怎么说”等意图或用户确认才计入求助证据。文本、转写和补录文字统一走 InputIntentResolver。英文 ASR 强制 language=en 的路径不能声称自动支持中文，应继续保留明确中文求助入口，或经真实样本验证自动检测策略。

验收：中英专有名词混用不被无条件降档；真实求助被识别；语音与文字有一致且可解释的规则。

### P2 · 强制调档弹窗不适合反复打断口语练习

证据：`ui/ChatScreen.kt` 的 `LevelSuggestionDialog`，以及交接说明“居中弹窗强制二选一”。

建议改为会话结束后的轻提示或不抢焦点的小卡片，显示“要不要试试慢速？”及一条可解释理由，提供“试试 / 暂时保持”。不展示貌似正式测评的三项模型分数；用户可以关闭自动建议。手动选档始终保留。

### 交付与文档准确性

- `docs/REVIEW-0.5.0.md:59` 的“同一调试签名，可覆盖安装”没有构建配置保证；当前没有统一 signingConfig。应写实际证书指纹和构建来源。
- 该文件说没有本地连接配置就“只能示例体验”，不准确：App 现有重新连接功能可在安装后配对，不需要把共享令牌重新编入 APK。
- 加入 `.gitignore` 不会移除已被 Git 跟踪的 6 个旧 APK；`git ls-files` 仍能看到。停止今后跟踪与凭据失效才有实际效果。清历史会改写仓库历史，需团队安排，不能擅自 force push。
- 云端 WAV 的日常与地道档实际均 1.0×，系统 TTS 日常为 0.92，试听与真实云端并不完全一致；现有 UI 有试听来源说明，但文档中的统一 0.80/0.92/1.00 容易误解。明确区分两种语音链路，或统一播放速率政策；变速不是模型生成了真正的连读。
- 0.4 数据里旧消息没有 difficulty，回退当前会话档位意味着旧音频会随会话档位改变；“每条历史消息档位保持”只能保证新生成消息。若要覆盖旧消息，在升级时一次性记录旧消息的默认档位。
- 服务端/网页未实现难度；宣传应限定 Android 端，不把设计预览页当在线功能。

## 3. 建议合并策略

在功能分支基线上逐项修复上述问题，保留消息档位与旧数据兼容；先补调档集成边界测试，再与主分支合并。不要只拷 UI 和 enum，否则会漏掉序列化、历史重生成和语音速率。

合并时保持 `applicationId` 和既定发布证书，不让成员电脑决定更新身份；下一个正式版本 `versionCode` 必须大于所有已分发版本。测试体验包 versionCode 7 不代表正式主分支已经升级。

本次同签名体验包保持组员提交行为，不宣称已修复本报告发现。具体编译、测试、lint、证书与凭据结果见交付目录的构建核验记录；原始源码仍保留在隔离目录，主项目功能源码未被覆盖。

实际验证：`:app:assembleDebug`、`:app:testDebugUnitTest`、`:app:lintDebug` 均成功，**109 个测试通过，0 失败/错误/跳过，lint 0 问题**。`apksigner verify` 通过，新包证书 SHA-256 与现有 0.4.0 一致。生成的 BuildConfig 服务地址/令牌均为空，全部 APK 条目扫描未发现本机已知运营凭据或共享服务令牌。不调用真实模型，不宣称已验证手机安装或新增变速行为。

## 4. 增量验收矩阵

| 类别 | 核心验收 |
|---|---|
| 旧数据 | 无 difficulty 的 0.4 记录可读；更新后会话/收藏/录音数量一致；新字段 round-trip |
| 档位 | 每档生成短回复；自由聊与复习目标不冲突；旧消息重生沿用旧档 |
| 语音 | 用户录音不变速；三档云端/系统回退各自速率可解释；异常机型回退可见 |
| 调档 | 降档不走升级审核；冷却隔离；取消/切后台/录音/更换会话无过期弹窗 |
| 求助 | 文字/语音/补转写按明确策略识别；专有名词中英混合不误报 |
| 发布 | 包名、versionCode、证书指纹符合升级策略；无共享凭据；新增行为有真机结果 |

现有版本真机通过按用户反馈接受。本次构建测试不自动证明新增功能已经真机通过，也不重复否定现有验收结果。
